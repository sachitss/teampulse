# AGENT ↔ BACKEND API CONTRACT — TeamPulse

**Status:** source of truth for both builds. The web backend (Step 1–12 of the SaaS prompt) exposes these endpoints; the Windows agent (Prompt B) consumes them. Neither side invents its own shapes — if something is missing here, update this file first, then both builds.

**Version:** v1
**Base URL:** `https://api.{yourdomain}/agent/v1`
**All traffic:** HTTPS only (TLS 1.2+). Reject plain HTTP.

---

## 1. Principles

- The agent is a **thin, honest collector**. It never decides policy; it fetches policy and obeys it.
- Every request is **tenant-scoped via the device token**. The agent never sends a tenant ID in the body; the server derives tenant + device + employee from the authenticated token. A body-supplied tenant/employee ID is ignored.
- Uploads are **idempotent and replayable**. The agent may resend anything after a crash or network loss; the server must deduplicate.
- The server is the clock of record for *policy*; the agent is the clock of record for *when an event happened* (it stamps events locally in UTC and may upload them late).

---

## 2. Conventions

| Topic | Rule |
|---|---|
| Timestamps | UTC, ISO 8601 with `Z`, millisecond precision: `2026-10-28T18:07:00.000Z`. Server converts to local time for display. |
| IDs | UUID v4, generated by whichever side owns the record. Agent generates `event_id`, `screenshot_id`, `batch_id`. |
| Idempotency | Every POST that writes data carries header `Idempotency-Key: <uuid>`. Retrying with the same key returns the original result and writes nothing new. |
| Content type | `application/json; charset=utf-8` unless stated otherwise. |
| Auth header | `Authorization: Bearer <access_token>` on every call except `/enroll`. |
| Clock skew | Server tolerates ±5 min skew on `recorded_at`. It never rejects an event for being "old"; retention handles age. |
| Errors | JSON body `{ "error": { "code": "...", "message": "...", "retryable": true|false } }` with the HTTP status below. |

### Error codes

| HTTP | code | Agent behaviour |
|---|---|---|
| 400 | `invalid_payload` | Log, drop the item (do **not** retry a malformed item forever). |
| 401 | `token_expired` | Refresh access token, retry once. |
| 401 | `device_revoked` | **Stop all collection, wipe local queue, show revoked status, exit.** |
| 403 | `policy_forbids` | Stop the specific feature, keep running. |
| 409 | `duplicate` | Treat as success (already stored). |
| 413 | `payload_too_large` | Split batch in half, retry. |
| 429 | `rate_limited` | Honour `Retry-After` header, back off. |
| 5xx | `server_error` | Exponential backoff, keep in local queue. |

## 3. Authentication & enrollment

### 3.1 Enroll a device
Admin generates a one-time **enrollment code** in the web app (short-lived, single-use, tenant-scoped). The code is entered once during agent install.

```
POST /enroll          (no Authorization header)
{
  "enrollment_code": "A1B2-C3D4-E5F6",
  "device": {
    "hostname": "PC-SALES-04",
    "os": "Windows 11 Pro 24H2",
    "agent_version": "1.0.0",
    "machine_fingerprint": "sha256:..."   // stable, non-reversible
  }
}
→ 200
{
  "device_id": "uuid",
  "employee_id": "uuid",            // whom the admin bound this code to
  "device_token": "opaque-long-lived-refresh-token",
  "access_token": "jwt",
  "access_token_expires_at": "2026-10-28T18:22:00.000Z"
}
```
The **device_token** is stored encrypted on disk (DPAPI, machine scope). It is the only long-lived secret. If the install is re-run on the same machine, enrollment must be idempotent on `machine_fingerprint`.

### 3.2 Refresh access token
```
POST /token/refresh   (no Authorization header)
{ "device_token": "..." }
→ 200
{ "access_token": "jwt", "access_token_expires_at": "...", "device_token": "..." }
```
Access tokens are short-lived (~15 min). The server **may rotate** the device_token on refresh; if a new one is returned, the agent must replace the stored copy atomically.

### 3.3 Revocation
Admin revokes a device in the web app. On the **next** `/token/refresh` or any authenticated call, the server returns `401 device_revoked`. The agent then stops, deletes its local queue and stored tokens, and reports revoked status in the tray UI.

## 4. Policy

The agent fetches policy on start, on every heartbeat interval, and whenever the server signals a change. Policy is **the only thing that turns features on or off**. The agent ships with everything off.

```
GET /policy
→ 200
{
  "policy_version": 7,                     // monotonically increasing
  "monitoring": {
    "work_schedule": {                     // local time, employee's tz
      "timezone": "Europe/Berlin",
      "windows": [ { "days": ["mon","tue","wed","thu","fri"], "start": "09:00", "end": "18:00" } ]
    },
    "session_mode": "schedule+manual",     // schedule | manual | schedule+manual
    "screenshots": {
      "enabled": true,
      "interval_seconds": 600,
      "jitter_seconds": 30,                // randomise so captures aren't predictable
      "image_format": "jpeg",
      "max_long_edge_px": 1280,
      "jpeg_quality": 70
    },
    "app_activity":      { "enabled": true, "capture_window_title": false },
    "website_activity":  { "enabled": true, "capture_full_url": false },  // domain only unless true
    "input_metrics":     { "enabled": true, "window_seconds": 60 },       // counts only, never content
    "file_activity":     { "enabled": false, "watched_paths": [], "store_hash": false },
    "exclusions": {
      "apps":        ["1password.exe", "keepass.exe", "bitwarden.exe"],
      "domains":     ["bank.example", "*.health.example"],
      "paths":       ["C:\\Users\\*\\Personal"]
    }
  },
  "privacy_pause": { "employee_can_pause": true, "max_pause_minutes": 60 }
}
```
When any feature is `enabled: false` or the current time is outside a work window (and no manual session is active), the agent **collects nothing for that feature**. Exclusions are matched before anything is recorded or uploaded.

## 5. Sessions & heartbeat

### 5.1 Session lifecycle
The agent reports session boundaries so the backend can reconcile tracked vs scheduled hours.
```
POST /sessions
Idempotency-Key: <uuid>
{
  "session_id": "uuid",                    // agent-generated
  "type": "start" | "break_start" | "break_end" | "resume" | "stop" | "privacy_pause_start" | "privacy_pause_end",
  "task_id": "uuid|null",                  // task chosen by employee at start
  "recorded_at": "2026-10-28T08:00:00.000Z",
  "reason": "string|null"
}
→ 202 { "accepted": true }
```

### 5.2 Heartbeat (also the command channel)
```
POST /heartbeat
{
  "agent_version": "1.0.0",
  "policy_version": 7,                      // what the agent currently has
  "active_session_id": "uuid|null",
  "queue_depth": 42,                        // unsynced items
  "capabilities": {                         // honest status, see §8
    "screenshots": "ok",
    "input_metrics": "ok",
    "file_activity": "permission_denied"
  }
}
→ 200
{
  "policy_version": 7,                      // if higher than agent's, re-fetch /policy
  "commands": [
    { "command_id": "uuid", "type": "capture_screenshot_now", "reason": "manager_request", "requested_by": "uuid" }
  ]
}
```
Commands are **acknowledged by acting and uploading the result** with the matching `command_id`. An immediate-screenshot command is honoured only if the device is online, a monitored session is active, and policy allows screenshots — otherwise the agent returns the result with `status: "refused_by_policy"`.

Default heartbeat interval: 60 s online. On failure, back off to a cap (e.g. 5 min) and keep queuing.

## 6. Event upload (batched)

One endpoint for all non-screenshot activity. Events are an array; the server unpacks by `kind`.

```
POST /events
Idempotency-Key: <batch_id>
{
  "batch_id": "uuid",
  "events": [
    {
      "event_id": "uuid",
      "kind": "app_activity",
      "recorded_at": "...", "ended_at": "...",
      "session_id": "uuid|null", "task_id": "uuid|null",
      "app": { "name": "Code.exe", "process": "Code", "window_title": null }
    },
    {
      "event_id": "uuid",
      "kind": "website_activity",
      "recorded_at": "...", "ended_at": "...",
      "session_id": "uuid|null", "task_id": "uuid|null",
      "web": { "domain": "github.com", "full_url": null }
    },
    {
      "event_id": "uuid",
      "kind": "input_metrics",
      "recorded_at": "...", "window_seconds": 60,
      "session_id": "uuid|null",
      "metrics": { "key_events": 220, "mouse_events": 540, "active": true }   // COUNTS ONLY
    },
    {
      "event_id": "uuid",
      "kind": "idle",
      "recorded_at": "...", "ended_at": "...",
      "session_id": "uuid|null",
      "idle": { "duration_seconds": 300, "resolution": "pending" }  // pending|kept|discarded|reassigned
    },
    {
      "event_id": "uuid",
      "kind": "file_activity",
      "recorded_at": "...",
      "session_id": "uuid|null", "task_id": "uuid|null",
      "file": { "event_type": "modified", "name": "report.xlsx", "path": "D:\\Work\\report.xlsx",
                "app": "EXCEL.EXE", "hash": null }
    }
  ]
}
→ 202
{ "accepted_event_ids": ["..."], "rejected": [ { "event_id": "...", "code": "invalid_payload" } ] }
```
**Dedup key = `event_id`.** Re-uploading a batch (same `batch_id`) or the same `event_id` in a different batch must not create duplicates. The server stores accepted IDs; rejected items are reported so the agent can drop them instead of retrying forever.

## 7. Screenshots (three-step, binary never touches the API)

### 7.1 Request an upload slot
```
POST /screenshots
Idempotency-Key: <screenshot_id>
{
  "screenshot_id": "uuid",
  "captured_at": "2026-10-28T10:10:00.000Z",
  "session_id": "uuid", "task_id": "uuid|null",
  "command_id": "uuid|null",               // set if this answers an immediate request
  "reason": "scheduled" | "manager_request",
  "image": { "format": "jpeg", "width": 1280, "height": 800, "bytes": 184210 }
}
→ 200
{ "upload_url": "https://storage.../signed-PUT?...", "expires_at": "...", "storage_key": "tenant/.../uuid.jpg" }
```
### 7.2 Upload the bytes
Agent does a direct `PUT` of the JPEG to `upload_url` (private object storage). The API server never receives the image.
### 7.3 Confirm
```
POST /screenshots/{screenshot_id}/confirm
{ "uploaded": true, "etag": "..." }
→ 200 { "status": "stored" }
```
If capture failed or was refused:
```
POST /screenshots/{screenshot_id}/confirm
{ "uploaded": false, "status": "refused_by_policy" | "capture_failed", "detail": "no active session" }
```
Viewing links for the dashboard are **short-lived signed GETs minted by the backend on demand** — never stored, never emailed.

## 8. Capability & diagnostics

The agent must tell the truth about what it can actually do on this machine. Each capability is one of: `ok`, `permission_denied`, `unsupported`, `disabled_by_policy`, `error`. These surface in both the tray UI and the admin dashboard. **The agent never fabricates data for a capability it cannot collect** — it reports the status and collects nothing.

```
POST /diagnostics
{
  "agent_version": "1.0.0",
  "capabilities": { "screenshots": "ok", "file_activity": "permission_denied", ... },
  "last_error": "string|null",
  "queue_depth": 0,
  "clock_offset_ms": 120
}
→ 202 { "accepted": true }
```

## 9. Offline sync rules (both sides must honour)

1. The agent persists every event in a **local encrypted queue (SQLite, DPAPI-protected key)** the instant it is captured, before any upload attempt.
2. Upload order is best-effort chronological, but the server must accept **out-of-order** and **late** events (reconciled by `recorded_at`).
3. Retry with exponential backoff + jitter, capped (e.g. 1s → 2s → … → 5 min). Never a tight retry loop.
4. An item is removed from the local queue **only** after a `202` lists its ID in `accepted` (or a `409 duplicate`, or a `400` telling the agent to drop it).
5. On `device_revoked`, the queue is wiped unsent.
6. Nothing captured outside an authorized session or against an excluded app/domain/path ever enters the queue in the first place.

---

## 10. What the contract forbids (enforced on both sides)

- No raw keystrokes, no typed text, no clipboard, no passwords or tokens — only `key_events`/`mouse_events` **counts**.
- No full URLs or window titles unless policy explicitly enables them.
- No screenshots outside an active, policy-permitted session.
- No covert mode: the tray status and monitoring indicator are not suppressible by the agent.
- No endpoint accepts a client-supplied tenant/employee override.
